## Current P0 update after L-001AD

- The L-001P integration (#23) succeeded in the final commit CI, and L-001Q (#24) now tests a journal-bound counter transition with matching dual witness receipts, full signed-history replay, mirror parity, current Owner manifest and a SQLite transaction barrier. Both remain **unmerged Draft PRs**.
- A matching counter/manifest pair is only a **diagnostic** result. No real independently protected TPM anchor, attested device binding, authenticated durable Prepared store or physical power-loss verification exists; ServiceOpen stays disabled.
- L-001R checks that a counter's earlier high-water record matches a replayed **signed historical prefix** (sequence, head, revocation root and then-current Owner manifest) before any modeled increment. A matching latest witness alone is not enough. These proofs depend on trusted external enrollment and retained signed journal history; physical and global freshness are still not guaranteed.
- L-001S explicitly models unacknowledged volatile writes vs. acknowledged simulated durable writes and all eight Prepare/Increment/Finalize cut points. A reboot preserves the simulated NV counter and acknowledged intent image but invalidates old handles. Those are *model semantics*, NOT physical persistence or anti-rollback protection.
- L-001T signs and verifies fixed-width intent records against an externally enrolled signer, device/Root/Writer scope and a separately maintained sequence/digest/counter replay fence. This is a strict *record authentication verifier*, not a durable signer provisioning, anti-rollback backend or authorization token.
- L-001U adds an authenticated **read boundary**, not a writable durable IntentStore: it verifies the signed record on every load against independently supplied signer and replay fence, rechecks all observed inputs, and rejects any prepare/finalize. Existing full journal replay and two-Witness consistency checks still run in the bounded PoC recovery route.
- L-001V adds **only** a deterministic model of an authenticated signed writer: it signs a canonical frame using an abstract external signer, atomically compares the old frame/fence/counter after signing, and simulates a single frame+fence CAS. It tests crash cuts and racing writers without changing hardware or ServiceOpen. A mutex is **not** independently authenticated durable CAS.
- L-001W extends the model-only CAS to change signer public key + epoch, record + external fence in one **in-memory** atomic step. Approval is an externally supplied *test fixture*, NOT a cryptographically authorized administrative action. Rotation is prohibited during Prepared recovery; reset or a stale old-key signed record fails closed.
- L-001X adds a **separate** diagnostic candidate preflight path: short SQLite transaction verifies the full Root/Owner signed history, mirror parity, dual Witness and exact old policy prefix; the actor releases all DB locks during external signing, and a second short transaction rejects altered snapshots **before** invoking an optional in-memory Prepared CAS. The L-001Q long-transaction path remains present and must **not** be used for real hardware. A journal append occurring after revalidation but before external CAS is still an unresolved TOCTOU.
- L-001Y **only in one journal instance** eliminates the post-second-check/pre-model-CAS append interleaving: signed append invalidates outstanding generation/ticket, while a final full-history/Witness replay and simulated Prepared CAS share a single in-memory gate (no SQLite transaction during model CAS). Ambiguous result forbids further reservations and a later emergency policy append marks Prepared stale without blocking revocation. A second process or direct SQLite connection **is not fenced**, and the reservation/quarantine disappears on restart.
- L-001Z adds another complete signed replay after model publication: a different journal instance or raw SQLite writer that changes evidence **during** the callback forces Conflict and a volatile stale quarantine rather than a false success. The modeled Prepared may still exist and rollback cannot be assumed. Changes **after** that replay and fresh actors after restart remain unfenced.
- L-001AA models a wholly separate reservation high-water across simulated reboot with one-shot generation/ticket CAS and no automatic recovery for Prepared. Critically, a raw SQLite writer that fails to notify the model is **undetectable**; its acceptance requires compulsory independently authenticated cross-process participation, not merely forwarding unverified `JournalView` structures.
- L-001AB adds Go, Kotlin, and JavaScript independent canonical CBOR decoders and signing transcript checks, using three shared golden vectors including 64-bit boundary cases, plus a CI job. This is candidate WIRE-01 evidence, **not** an independently frozen protocol or end-to-end peer-admission security approval.
- A machine-readable `docs/acceptance/l001.json` now explicitly lists all nine L-001 A–D acceptance gates. `scripts/l001_gate.py` rejects unsupported completion claims and fails release mode when any gate or required signoff is missing.
- L-001AC integrates original L-001A isolated mTLS Peer channel into the current stacked Rust workspace, including trust-pinned Ed25519 test certificates, encrypted Space/Peer/epoch binding and malicious bearer tests. This is a **nonproduction channel PoC**; an authenticated Peer is not thereby authorized for any Resource, and the existing disabled `loomd` still cannot ServiceOpen.
- L-001AD runs the complete Rust library/unit/PoC suite on GitHub-hosted Windows and macOS in addition to Ubuntu. This demonstrates **host compiler/test portability only**. No driver, packet interception, signed system extension entitlement, Android device, VPN routing or actual platform acceptance is present.
- Production design must remove long-running external hardware I/O from all SQLite write transactions **and process locks**. Independently authenticated real durable Prepared intent, hardware-backed signer/fence CAS, cross-process journal-to-CAS reservation fencing, audited key-rotation authorization, TPM provisioning, real power-loss and cross-host adversarial acceptance remain blockers.

## Critical release blockers (P0)

1. **Canonical policy ledger & legacy migration:** No authenticated, one-way migration from the old revocation-only tables to the unified Owner lifecycle. Legacy databases are intentionally refused; the read-only audit produces evidence, not an authorized migration.
2. **Independent rollback resistance:** No production `IndependentUnifiedPolicyAnchor`. Neither SQLite, in-memory counters, the TPM2 read-only probe nor a numeric TPM counter alone authorize the policy high-water. Missing/rolled-back intent, reset, stolen TPM identity and crash windows remain deployment blockers.
3. **Trusted enrolment and witness freshness:** Root pin, Owner manifest, witness quorum, secure time, replay under a transaction, device attestation and global witness anti-eclipse policies lack production-grade end-to-end binding.
4. **Admission and transport:** No verified handshake-to-policy-to-ServiceOpen commit path; no revocation-to-session termination guarantee, membership convergence, relay path validation or tested two-Peer LAN file-read/revoke acceptance.
5. **Platform and rollout:** Android VPN, Windows filtering, macOS entitlements, LAN/WAN interoperability, multi-process crash/power-loss and real-device TPM failure-injection have not passed. Release/license review remains open.
